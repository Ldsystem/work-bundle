WorkBundle Toolkit · Execution Flow

Vertical Dependency Roadmap

A serial-first roadmap for external execution. Formal blocker joins are preserved, but the recommended working order minimizes context switching and avoids opening every branch at once.
The important idea We do not have to develop every branch together. Build one useful vertical spine first, then add side capabilities only when the trunk reaches the node that needs them.

Recommended serial-first path

least context switching
WOR-31 · Provider-neutral adapter protocol
What we get: one stable interface for fake, ACP, cloud, cancellation, provider status and result collection.
↓
WOR-32 · FakeExecutor adapter + deterministic fixtures
What we get: Execution Flow can execute and fail predictably without spending provider quota. This becomes the test bed for routing.
↓
WOR-35 · Concrete executor registry
What we get: a structured catalog of agent/model/provider capabilities, constraints, cost, latency, reliability and evidence.
↓
WOR-36 · Deterministic executor ranking
What we get: the same task + registry state always produces an explainable concrete executor choice.
↓
WOR-37 · Quota/provider fallback + real routing control
What we get: a usable router. It can select an executor, dispatch through the adapter protocol, detect quota/provider failure and fall back without weakening the WorkBundle task contract.
At this point the core routing engine exists
WOR-33 · ACP external executor
What we get: visible delegation to a real ACP-capable agent instead of only the fake adapter.
Requires WOR-31 + WOR-32
WOR-38 · Outcome-based routing evidence
What we get: routing preferences can improve from WorkBundle-observed success/failure evidence instead of executor self-rating.
Requires WOR-37
↘          ↙
WOR-39 · End-to-end multi-executor proof + diagnostics
What we finally get: a deterministic demonstration of WorkBundle task → executor ranking → fallback/delegation → ACP/fake executor → executor-result → WorkBundle validation → outcome evidence.
Core Execution Flow proven
Formal blockers: WOR-37 + WOR-33 + WOR-38

Cross-branch joins

WOR-37 is where Adapter branch A and Routing branch B first truly meet. It formally requires WOR-31, WOR-32 and WOR-36.

WOR-39 is the final convergence. It formally waits for WOR-37, WOR-33 and WOR-38.

WOR-42 ↔ WOR-36 is currently a relationship, not a formal blocker. WOR-36 already specifies fail-closed defensive validation until WOR-42 lands.

WOR-28 → WOR-29 is a separate WorkBundle hardening chain. It does not formally block WOR-39 today; treat WOR-29 as a release-quality gate before broadly trusting external execution.

Branches we can deliberately postpone

not needed for the first usable core
WOR-40 · Async cloud transport
Depends on WOR-31. Eventually gives provider job/session state, asynchronous completion and cloud result collection.
WOR-34 · Optional MCP frontend
Depends on WOR-31. Eventually gives an MCP-facing API over Execution Flow rather than a new orchestration engine.
WOR-27 → WOR-30 · Transport/no-retrieval research
Decision work only. It asks whether a request wrapper or future retrieval exception is necessary. Neither is required for baseline Execution Flow.

Low-exhaustion working sequence

one vertical slice at a time
Step 1
WOR-31 → WOR-32
Build the execution foundation and fake harness.
Step 2
WOR-35 → WOR-36 → WOR-37
Build the router against that harness.
Step 3
WOR-33 → WOR-38
Add real ACP execution, then feedback evidence.
Step 4
WOR-39
Merge the branches and prove the complete flow.
Practical recommendation Start with WOR-31. Do not open four implementation fronts. Finish WOR-31 → WOR-32 first; then move into the routing chain. WorkBundle hardening (WOR-42 and WOR-28 → WOR-29) can be scheduled as deliberate checkpoints rather than a permanently parallel stream.
